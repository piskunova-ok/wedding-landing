# wedding-landing

**Лендинг-приглашение на свадьбу «Анна & Михаил»** — одностраничный тёплый осенний сайт-приглашение с формой подтверждения присутствия (RSVP), страницей для организаторов и backend-частью без единой сторонней зависимости.

Свадьба: **24 сентября 2026, 16:00**, Усадьба «Мещерская», г. Гусь-Хрустальный, ул. Интернациональная, д. 105.

---

## Задача, которую решает проект

Организаторам свадьбы нужно собрать ответы гостей: кто придёт, в каком количестве, есть ли особые пожелания по меню. Готовые конструкторы типовых страниц обычно платные, не хранят данные в гостевой базе, а «коробочные» решения по RSVP — отдельная подписка.

Этот проект решает задачу **полностью самостоятельно и без бюджета**:

- красивая страница-приглашение, которую можно разослать по ссылке;
- форма RSVP, которая сохраняет ответы в базу (Supabase/PostgreSQL) или в локальный файл;
- уведомление организаторов о каждом новом ответе в Telegram;
- страница `/admin.html` со статистикой и выгрузкой ответов в CSV;
- деплой на Netlify с serverless-функцией — свой выделенный сервер не нужен.

Ноль платных подписок, ноль сторонних SDK, ноль сборщиков.

## Для кого предназначен

| Роль | Что делает в проекте |
|---|---|
| **Гости свадьбы** | Открывают ссылку, смотрят программу дня, дресс-код, локацию и подтверждают присутствие одной формой |
| **Организаторы** (Анна и Михаил) | Открывают `/admin.html` под паролем, видят статистику и выгружают ответы в CSV |
| **Разработчики** | Берут проект как рабочий пример landing + API + serverless + server-side валидации без фреймворков |

## Основные функции и сценарии использования

### Публичная страница (`index.html`)

- **Hero-экран** с именами пары, датой и плавным появлением контента.
- **Липкая навигация** с переходами по секциям; на мобильных — бургер-меню.
- **Секция деталей**: дата, время, место проведения, адрес, ссылка на Яндекс.Карты.
- **«Наша история»** — блок с фото пары.
- **Галерея с лайтбоксом**: увеличение фото по клику, навигация стрелками `←`/`→`, закрытие по `Esc` или клику на фон, скролл страницы блокируется на время просмотра.
- **Обратный отсчёт** до даты свадьбы (дни/часы/минуты/секунды). После наступления даты таймер заменяется благодарностью гостям.
- **Дресс-код** с визуальной палитрой разрешённых оттенков.
- **Программа дня** в виде таймлайна с 6 пунктами от 16:00 до 23:00.
- **Форма RSVP**: имя и фамилия, выбор присутствия, количество гостей (1–4), пожелания по меню.
- **Блок «Как добраться»** с адресом и кнопкой на карту.
- **Финальный экран** с благодарностью.
- **Адаптивная вёрстка** и плавные анимации появления при скролле (`IntersectionObserver`).
- **Кастомная страница 404** в стиле сайта.

### Форма RSVP: сценарий отправки

1. Гость заполняет форму — **валидация сначала на клиенте** (имя от 2 символов, выбран ответ, гости 1–4, комментарий до 500 символов) с конкретным сообщением об ошибке под полем.
2. Запрос уходит в первую доступную точку: **`POST /api/rsvp`** (локальный сервер) → при её отсутствии — **`POST /.netlify/functions/rsvp`** (Netlify). Фоллбэк работает автоматически: 404 от статики или обрыв сети переключают на следующий URL.
3. **Повторная отправка блокируется** на время запроса (кнопка «Отправляем…»).
4. Ответ принимается **с серверной валидацией** — та же проверка, что и на клиенте, плюс rate-limit.
5. При успехе форма скрывается и показывается благодарность: отдельный текст для тех, кто придёт, и для тех, кто не сможет.
6. При ошибке выводится сообщение с сервера, форма снова разблокируется.

### Backend: два варианта на выбор

| | `server.js` (локально) | `netlify/functions/rsvp.js` (деплой) |
|---|---|---|
| Назначение | Разработка и просмотр на своём компьютере | Рабочая версия в проде |
| Статика | Раздаёт сам: HTML, CSS, JS, `img/` | Раздаёт Netlify |
| Хранилище | Всегда `data/rsvp.json` + **дубль в Supabase**, если задан ключ | Только Supabase (у serverless-функции нет диска) |
| Rate-limit | 10 запросов / 10 мин на IP | 20 запросов / 10 мин на IP |
| Уведомления | Telegram + вывод в консоль | Telegram (с таймаутом 8 с) |
| Данные в коде | Только встроенные модули `http`/`fs`/`path` | Только встроенный `fetch` |

Общее поведение: сервер **не доверяет клиенту** — имя, ответ, количество и длина комментария перепроверяются на сервере; ошибка возвращает `400` с текстом на русском.

### Просмотр ответов организаторами (`admin.html`)

- Вход по паролю — `ADMIN_SECRET` из переменных окружения; ключ запоминается в `sessionStorage`, страница помечена `noindex, nofollow`.
- **Четыре карточки статистики**: всего ответов / придут / не смогут / суммарное число гостей.
- **Таблица** с датой, именем, статусом, числом гостей и пожеланиями по меню.
- **Фильтр-бейджи** «Придёт ❤️» / «Не сможет».
- **Кнопка «Обновить»** и **«Скачать CSV»** — файл `rsvp-ответы.csv` с BOM, корректно открывается в Excel и Google Sheets.
- Список приходит с сервера **без IP-адресов** — IP не покидает backend.

### Безопасность и ограничение доступа

- `netlify.toml` закрывает от посторонних при деплое: `/data/*`, `/server.js`, `/package.json`, `/supabase.sql`, `/.env*` — всё отдаёт `404`.
- В `supabase.sql` таблица создаётся с **CHECK-ограничениями** (длина имени, допустимые значения ответа, число гостей 1–4) и включённым **RLS без политик** — читать и писать может только сервисный ключ, напрямую из браузера не получится.
- Фото `img/*` кэшируются на сутки.

| Слой | Технологии |

| Хранилище | Supabase (PostgreSQL + REST Data API) или локальный `data/rsvp.json` |

| Деплой | Netlify: статический хостинг + serverless-функции, `netlify.toml` |
| Шрифты | Google Fonts: Cormorant Garamond, Manrope, Marck Script |

## Установка, настройка и запуск

### 1. Требования

- **Node.js 18 или новее** (нужен глобальный `fetch`).
- Git — только если планируете отправку в репозиторий.
- Аккаунт [Supabase](https://supabase.com) — необязательно, но нужен для продакшена.

### 2. Настройка переменных окружения

```bash
cp .env.example .env
```

Заполните `.env`:

| Переменная | Обязательна | Назначение |
|---|---|---|
| `PORT` | нет (по умолчанию `3000`) | Порт локального сервера |
| `SUPABASE_URL` | для продакшена | URL проекта Supabase |
| `SUPABASE_SERVICE_KEY` | для продакшена | Service key — доступ только на сервере, **никогда не попадает во фронтенд** |
| `ADMIN_SECRET` | **да** | Пароль для просмотра ответов на `/admin.html`. Если не задан, действует пароль по умолчанию `anna-mikhail-2026` — обязательно замените |
| `TELEGRAM_BOT_TOKEN` | нет | Токен бота для уведомлений о новых ответах |
| `TELEGRAM_CHAT_ID` | нет | ID чата, куда слать уведомления |
| `RSVP_NOTIFICATION_EMAIL` | нет | Только пометка получателя — **письмо на самом деле не отправляется**, значение уходит в лог сервера |

Файл `.env` входит в `.gitignore` и в репозиторий не попадает. В GitHub значения задаются в **Settings → Secrets and variables → Actions / переменные окружения хостинга**.

### 3. База данных Supabase (для продакшена)

1. Создайте проект в Supabase.
2. Откройте **SQL Editor**, выполните содержимое `supabase.sql` — он создаёт таблицу `public.rsvp` с ограничениями и включённой RLS. Скрипт безопасен при повторном запуске.
3. Передайте `SUPABASE_URL` и `SUPABASE_SERVICE_KEY` в переменные окружения.

Без Supabase проект всё равно работает — ответы просто сохраняются в `data/rsvp.json`.

### 4. Локальный запуск

```bash
npm start
# или
node server.js
```

Сервер поднимется на <http://localhost:3000>:

- **Главная страница** — `http://localhost:3000/`
- **Ответы гостей** — `http://localhost:3000/admin.html`, вход по `ADMIN_SECRET`

В консоли выводится, включён ли Supabase и не остался ли пароль по умолчанию.

### 5. Деплой на Netlify

1. Запушьте репозиторий в GitHub.
2. В Netlify: **Add new site → Import an existing project** и выберите репозиторий. Настройки сборки берутся из `netlify.toml` (`publish = "."`, `functions = "netlify/functions"`) — менять ничего не нужно.
3. В **Site settings → Environment variables** задайте: `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `ADMIN_SECRET` (обязательно), а также `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `RSVP_NOTIFICATION_EMAIL` (по желанию).
4. Задеплойте — форма будет хранить ответы в Supabase через `/.netlify/functions/rsvp`.

Важно: `server.js` на Netlify не запускается (это статический хостинг), для него в браузере предусмотрен автоматический фоллбэк на serverless-функцию.

### 6. Как обновить дату, адрес и тексты

Всё содержимое меняется прямо в `index.html` — секции подписаны комментариями `<!-- НАВИГАЦИЯ -->`, `<!-- HERO -->`, `<!-- ДРЕСС-КОД -->` и т. д. Дату для обратного отсчёта задайте в `script.js`:

```js
var CONFIG = {
  weddingDate: '2026-09-24T16:00:00',   // ← формат YYYY-MM-DDTHH:MM:SS
  endpoints: { rsvp: ['/api/rsvp', '/.netlify/functions/rsvp'] }
};
```

## Текущие ограничения и планы развития

### Ограничения

**Безопасность**

- Доступ к `admin.html` защищён **одним общим паролем**, который передаётся как query-параметр `?key=...`. Он попадает в историю браузера и логи хостинга — полноценных сессий и учётных записей нет. Сама страница опублична, закрыт только запрос данных.
- Rate-limit хранится **в памяти процесса**: сбрасывается при перезапуске и не общий между инстансами serverless-функции — это защита от случайных дублей, а не от продуманной атаки.
- `ADMIN_SECRET` в коде имеет значение по умолчанию `anna-mikhail-2026`; если переменная не задана, работает именно оно.

**Функциональность**

- **E-mail-уведомления не реализованы.** `RSVP_NOTIFICATION_EMAIL` только выводится в консоль сервера — письма на самом деле не отправляются.
- Дублирующая запись в Supabase внутри `server.js` не `await`-ится: при ошибке ответ гостю всё равно вернётся `200`, а проблема уйдёт только в лог.
- Уведомления в Telegram — best-effort: сбой не влияет на приём ответа, но и не ретраится.
- Нет редактирования, удаления и дедупликации ответов — принятые заявки только накапливаются.
- Нет аутентификации гостя (гости не опознаются), поэтому один человек может отправить форму несколько раз.
- Ответы хранятся в одном массиве: при большом числе гостей `data/rsvp.json` станет неудобным, а Supabase-таблица не имеет индексов под отчёты.

**Контент и интерфейс**

- Дата, имена пары, адрес и программа дня **захардкожены** в `index.html` и в `CONFIG.weddingDate` в `script.js` — единого файла конфигурации контента нет.
- Интерфейс только на русском языке, без переключателя.
- Фотографии — **AI-генерированные изображения (Gemini)**, не реальные снимки пары.
- Сжатия и конвертации в WebP нет: страница тянет ~16 МБ картинок; `loading="lazy"` есть только у «ленивых» фото секций, hero и фоны грузятся сразу.
- Лайтбокс не поддерживает свайпы на тач-устройствах и не ограничивает фокус клавиатуры (tab-trap) — только стрелки и `Esc`.
- Обратный отсчёт считается в браузере от системного времени, при расхождении часов отобразит неверное значение.

**Процесс**

- Тестов, линтера и CI нет.
- Сборка и минификация отсутствуют — фронтенд идёт как есть, «так и задумано» для этого размера проекта.

### Планы развития

**Короткий горизонт**

1. Задать свой `ADMIN_SECRET` и перевести админку на `sessionStorage`/заголовок вместо query-параметра.
2. Сжать фото и перевести их в WebP с `<picture>` — основной выигрыш по скорости загрузки.
3. Вынести дату, адрес и тексты в единый `config.js`.
4. Реализовать реальную отправку e-mail через SMTP-провайдер или SendGrid.

**Средний горизонт**

5. Заменить общий пароль админки на авторизацию через Supabase Auth с ролями.
6. Экспорт в Excel-формат по-настоящему, фильтры по дате и статусу, поиск по имени.
7. Добавить редактирование и удаление ответов прямо в `admin.html`.
8. Антибот-защита формы: honeypot-поле или решение вроде Cloudflare Turnstile.
9. Очередь отправки для уведомлений, чтобы Telegram-ошибки не терялись.

**Дальний горизонт**

10. Версионирование и публикация статики на CDN, сервисную мониторинг формы.
11. Календарное приложение (`.ics`) в скачивание для гостей и таймаут-кнопки.
12. Режим «шаблона»: вынести весь свадебный контент в `config.json`, чтобы проект можно было переиспользовать для другой пары без правки HTML.
13. i18n: английская версия страницы.
